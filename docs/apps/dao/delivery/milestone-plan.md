# DAO delivery milestones

## Accepted history

M0 established the product/source contract. M1 built the domain and mocks.
M2 delivered and received acceptance for the mock product and guarded beta review.
V1 WP8 was historically accepted and integrated; its proof-heavy feed contract
is superseded by the user-authorized V2 reset. See the unchanged historical
acceptance rows in [status](status.md).

## Governance Apps V2 reset

Complete revised WP8, WP11 and WP12 together: small structural schema,
field/source mapping, state-read contract, optional exact content, script
integrity, real static-feed transport/adapter/routes, current-wallet read overlay,
mock action consequences, tests, measured budgets and producer handoff.

Consumer external review and producer handoff approval are complete for the exact
range recorded in [status](status.md). The approved consumer is integrated;
the [integration record](evidence/feed-v2/integration.md) records its local checks.
WP9 producer implementation is the next dependency in its own authorized task,
with producer lane and target preflight still required. This consumer milestone
does not complete actual producer interoperability or later release gates.

## Producer and interoperability

WP9 implements the separate existing Rust process after approval, using bounded
all-proposal state refresh and canonical event history. It retains scripts and
content, handles reorgs and publishes validated immutable candidates safely.
No historical simulation, trace classifier or storage reconstruction is required.

WP10 validates actual producer-generated bytes through this consumer's full read
path and routes. Include real deployment/source agreement, node hash-read/log
capabilities, complete acquisition, restart/reorg recovery, stale publication
protection and content/script durability. Small coordinated V2 amendments may
follow evidence. Consumer fixtures do not satisfy this milestone.

## Publication and writes

WP13 implements current forum validation and durable canonical content
publication. WP14 implements governance writes with live action-specific
eligibility and exact-data preparation through shared useTx. WP15 implements
fresh actual Voting.execute simulation and commitment checks. No write is
enabled by the read reset.

## Contract execution and lifecycle UAT

WP16 supplies an appropriate contract-executed test/fork environment without
building a second indexer. WP17 runs the producer and consumer together across
creation/ID zero, voting/replacement/zero events, both Veto paths, Flag/retracted,
signals, time/config changes, execution/revert and reorg recovery. Record origin
and exact bytes. Obtain explicit lifecycle UAT acceptance.

## Rollout

WP18 verifies live operations, existing protected hosts, feature flags,
monitoring, rollback and content/script durability. Production approval precedes
production exposure and any Snapshot-link cutover. Nothing in this reset changes
infrastructure, publishes a feed, deploys or submits a transaction.
